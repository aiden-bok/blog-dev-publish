2. Next.js, Prisma, PostgreSQL 테스트 작성 방법

Vitest로 컴포넌트를 테스트하고, Prisma Client를 mock으로 대체하는 단위 테스트와 Docker PostgreSQL을 쓰는 통합 테스트, Playwright E2E 실행 방법을 정리했습니다.

Next.js 앱의 테스트는 층에 따라 방법이 다릅니다. 컴포넌트는 Vitest와 React Testing Library로 렌더링해서 확인하고, Prisma 코드는 mock(가짜 객체)으로 대체해 DB 없이 확인하거나 Docker의 PostgreSQL에 prisma migrate deploy로 테이블을 만든 뒤 실제로 확인하며, 화면 흐름은 Playwright로 확인합니다. 도구를 고르는 기준은 1. Next.js 테스트 종류와 도구에 정리해 두었습니다.

이 글의 코드는 Next.js, Prisma, Playwright 공식 문서(2026-11-04 확인)의 예시를 바탕으로 합니다. 작성 환경에서는 코드를 직접 실행하지 못해 실행 결과는 싣지 않았습니다. 그대로 복사하기 전에 프로젝트의 버전에 맞는지 확인해야 합니다.

컴포넌트 테스트: Vitest와 React Testing Library#

Vitest로 컴포넌트를 테스트하려면 Vitest, React 플러그인, jsdom, React Testing Library를 개발 의존성으로 설치합니다. Next.js 문서가 안내하는 TypeScript 프로젝트 기준 명령은 다음과 같습니다. (How to set up Vitest with Next.js, Next.js Documentation)

npm install -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/dom vite-tsconfig-paths

프로젝트 루트에 vitest.config.mts를 만들고 테스트 환경을 jsdom으로 지정합니다.

import { defineConfig } from 'vitest/config'
import react from '@vitejs/plugin-react'
import tsconfigPaths from 'vite-tsconfig-paths'

export default defineConfig({
  plugins: [tsconfigPaths(), react()],
  test: {
    environment: 'jsdom',
  },
})

package.json의 scripts에 "test": "vitest"를 추가한 뒤 npm run test로 실행합니다. 이 명령은 기본적으로 파일 변경을 감시하며 계속 실행됩니다. 테스트 파일은 문서의 예시처럼 __tests__/page.test.tsx에 두거나 app 폴더 안에 함께 둘 수 있습니다.

import { expect, test } from 'vitest'
import { render, screen } from '@testing-library/react'
import Page from '../app/page'

test('Page', () => {
  render(<Page />)
  expect(screen.getByRole('heading', { level: 1, name: 'Home' })).toBeDefined()
})

이 테스트는 Page 컴포넌트를 렌더링한 뒤 이름이 Home인 1단계 제목이 화면에 있는지 확인합니다. 이름이 겹치는 요소가 여러 개면 getByRole이 오류를 내므로, 헷갈리면 역할과 이름을 함께 지정해야 합니다.

async Server Component는 이 방법으로 테스트하지 못합니다. Next.js 문서는 Vitest가 async Server Component를 지원하지 않으므로 E2E로 확인하라고 안내합니다. 데이터를 가져오는 Server Component가 많은 앱이라면 컴포넌트 테스트보다 E2E 비중이 커집니다.

단위 테스트: Prisma Client를 mock으로 대체#

Prisma Client를 mock으로 바꾸면 DB 없이 비즈니스 로직만 빠르게 확인할 수 있습니다. Prisma(ORM, Object-Relational Mapping: 객체와 관계형 DB를 연결하는 도구) 공식 가이드는 Jest와 jest-mock-extended 조합을 씁니다. 방식은 두 가지입니다. (Unit testing, Prisma Documentation)

  • 싱글톤 방식: client.ts에서 만든 Prisma Client 모듈을 jest.mock으로 통째로 깊은 mock(mockDeep<PrismaClient>())으로 바꾸고, 테스트마다 초기화합니다. 이 파일을 jest.config.js의 setupFilesAfterEnv에 등록합니다.
  • 의존성 주입 방식: 함수가 Prisma Client를 인자로 받게 만들고, 테스트에서는 createMockContext로 만든 mock을 넘깁니다.

테스트에서는 user.create 같은 모델 메서드가 돌려줄 값을 먼저 정하고, 테스트할 함수를 호출해 결과를 비교합니다. mock은 쿼리 자체가 맞는지는 알려 주지 않습니다. 잘못된 where 조건이나 유니크 제약 위반은 mock으로는 통과하므로, 쿼리가 중요한 코드는 아래 통합 테스트로 한 번 더 확인합니다.

통합 테스트: Docker의 PostgreSQL에 실제로 연결#

통합 테스트는 테스트용 PostgreSQL을 띄워 놓고 Prisma로 진짜 쿼리를 실행합니다. Prisma 공식 가이드는 docker compose로 컨테이너를 만들고, 마이그레이션을 적용하고, 테스트가 끝나면 컨테이너를 지우는 순서를 안내합니다. (Integration testing, Prisma Documentation)

  1. docker-compose.yml에 postgres 서비스를 정의하고 호스트 포트 5433을 컨테이너 5432에 연결합니다. 사용자, 비밀번호, DB 이름은 테스트 전용 값으로 정합니다.
  2. .env.test에 DATABASE_URL="postgresql://prisma:prisma@localhost:5433/tests" 같은 접속 주소를 둡니다.
  3. docker compose up -d로 컨테이너를 시작합니다.
  4. prisma migrate deploy로 prisma/migrations/의 마이그레이션을 적용해 테이블을 만듭니다.
  5. 테스트는 beforeAll에서 필요한 데이터를 넣고, jest -i처럼 한 번에 하나씩 순서대로 실행합니다. 테스트가 같은 DB를 함께 쓰기 때문입니다.
  6. afterAll에서 deleteMany()로 데이터를 지우고 $disconnect()를 호출합니다. 외래 키가 있으면 자식 테이블부터 지워야 합니다.
  7. 끝나면 docker compose down으로 컨테이너를 지웁니다.

운영 DB의 접속 주소를 .env.test에 넣지 않도록 주의해야 합니다. 테스트가 deleteMany()로 데이터를 지우기 때문에, 주소가 잘못 지정되면 운영 데이터가 삭제됩니다. localhost와 테스트 전용 포트인지 확인하는 습관이 필요합니다.

컨테이너를 직접 관리하기 번거로우면 Testcontainers를 쓸 수 있습니다. npm install @testcontainers/postgresql --save-dev로 설치하고, 컨테이너를 시작한 뒤 getConnectionUri()로 접속 주소를 얻어 쓰는 방식입니다. (PostgreSQL Module, Testcontainers for Node.js) 이 경우에도 Docker가 실행 중이어야 하고, 얻은 주소를 Prisma의 DATABASE_URL로 넘기는 부분은 직접 작성해야 합니다.

E2E 테스트: Playwright#

Playwright는 npm init playwright@latest로 설치하고 npx playwright test로 실행합니다. 기본으로 헤드리스(화면 없음)로 병렬 실행하고, --headed를 붙이면 브라우저 창이 보이며, --project=chromium으로 브라우저를 하나만 고르고, --ui로 UI 모드를 엽니다. (Installation, Playwright) Node.js는 최신 22.x, 24.x, 26.x가 필요합니다.

E2E 테스트는 앱이 실제로 떠 있어야 하므로 보통 next build와 next start로 띄운 서버를 대상으로 합니다. 이때 앞의 통합 테스트와 같은 테스트용 DB를 연결하면 회원 가입, 로그인 같은 시나리오를 운영 데이터와 분리해서 확인할 수 있습니다. 시나리오를 한 번에 길게 묶으면 실패했을 때 원인을 찾기 어려우므로, 핵심 흐름 몇 개만 E2E로 두고 나머지는 앞의 단위, 통합 테스트로 확인합니다.

용어 설명#

jsdom#

Node.js 안에서 브라우저의 DOM을 흉내 내는 JavaScript 라이브러리입니다. 브라우저 없이 컴포넌트를 렌더링해 볼 수 있습니다. (jsdom, GitHub)

mock#

테스트에서 실제 객체 대신 쓰는 가짜 객체입니다. 반환값을 미리 정해 두고, 호출됐는지 확인할 수 있습니다. (Vitest Mocking, Vitest)

ORM#

Object-Relational Mapping. 코드의 객체와 관계형 데이터베이스의 테이블을 연결해 주는 도구입니다. (Prisma ORM, Prisma Documentation)
