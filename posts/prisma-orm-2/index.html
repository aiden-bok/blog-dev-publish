2. ORM과 SQL 직접 작성, AI 도구와의 궁합

ORM을 쓰는 경우와 SQL을 직접 쓰는 경우의 장단점을 비교하고, AI 도구로 개발할 때 Prisma가 주는 이점과 주의점을 정리했습니다.

1. Prisma ORM 처음 써 보기와 다른 ORM과의 비교에서 이어지는 글입니다. 이번에는 ORM(Object-Relational Mapping: 객체 관계 매핑)을 아예 쓰지 않는 선택지와 비교하고, AI 도구로 개발할 때 ORM이 어떤 영향을 주는지 정리합니다. 기준은 1편과 같은 Prisma 7 문서(2026-11-01 확인)입니다.

ORM을 쓸 때와 쓰지 않을 때#

ORM 없이 개발한다는 것은 데이터베이스 드라이버로 SQL(Structured Query Language: 구조화 질의 언어) 문장을 직접 보내고 결과 행을 코드의 객체로 옮기는 일을 직접 한다는 뜻입니다. Prisma 문서가 꼽는 ORM의 장점은 반복되는 CRUD(Create, Read, Update, Delete: 생성, 조회, 수정, 삭제) 코드가 줄고 SQL을 거의 몰라도 쓸 수 있다는 것입니다. 단점으로는 객체와 테이블 사이의 개념 차이(impedance mismatch), 스키마가 바뀔 때 객체를 맞춰 주는 부담, 넓은 API, 일부 복잡한 쿼리의 표현 어려움을 듭니다. (Is Prisma an ORM?)

이를 뒤집으면 SQL 직접 작성의 성격이 나옵니다.

구분ORM(Prisma 기준)SQL 직접 작성
반복 코드CRUD는 메서드 호출로 끝남쿼리와 결과 매핑을 직접 작성
타입스키마에서 자동 생성직접 선언하거나 별도 도구 필요
마이그레이션스키마 변경에서 파생SQL 파일을 직접 관리
복잡한 쿼리표현이 어려우면 raw SQL로 우회제약 없음
학습 비용ORM 고유 API를 배워야 함SQL만 알면 됨

둘은 배타적이지 않습니다. Prisma도 raw SQL을 실행할 수 있고, .sql 파일에서 타입을 만들어 주는 TypedSQL은 typedSql 미리보기 기능을 켜면 쓸 수 있습니다. 단순한 읽기와 쓰기는 Prisma Client로, 집계나 복잡한 JOIN(조인: 여러 테이블을 키로 묶어 조회하는 쿼리)은 SQL로 나누는 구성이 현실적입니다. (TypedSQL)

트랜잭션처럼 데이터베이스 동작을 세밀하게 다뤄야 할 때는 ORM이 숨긴 부분을 알아야 합니다. Prisma 8 문서에는 트랜잭션에 타임아웃이 없고 쓰기 충돌을 자동으로 재시도하지 않으므로, 필요하면 데이터베이스 설정과 재시도 코드를 직접 챙기라고 나와 있습니다. (Transactions) 이 내용은 8 기준이라 7에서는 다를 수 있습니다. 어느 쪽이든 ORM을 쓴다고 데이터베이스 지식이 필요 없어지지는 않습니다.

AI 도구로 개발할 때#

이 부분은 공식 문서에서 확인한 사실과 제 판단을 나누어 적습니다. 직접 측정한 결과는 없습니다.

문서에서 확인한 사실부터 보면, Prisma는 AI 도구를 위한 장치를 몇 가지 제공합니다. Prisma MCP(Model Context Protocol: AI 도구가 외부 서비스와 연결하는 규약) 서버(https://mcp.prisma.io/mcp)는 Claude Code, Cursor, VS Code 같은 도구에 연결해 데이터베이스 관리와 SQL 실행, 문서 검색을 맡깁니다. 그리고 AI 에이전트가 prisma migrate reset --force 같은 파괴적 명령을 실행하면 Prisma CLI가 막고, 사용자가 명시적으로 동의한 뒤 PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION 환경 변수를 설정해야 다시 실행되게 합니다. (Prisma MCP server)

여기서부터는 제 판단입니다. ORM의 장점은 타입에서 나온다고 봅니다. AI가 만든 쿼리에 없는 필드나 잘못된 관계가 들어 있으면 TypeScript 컴파일 단계에서 걸러지므로, 코드를 읽기 전에 틀린 부분을 알 수 있습니다. 스키마 파일 하나에 모델 전체가 모여 있어서 AI에게 맥락을 주기 쉽다는 점도 있습니다. 반대로 단점은 AI가 지식이 오래된 상태로 옛 문법을 쓸 수 있다는 것입니다. Prisma 7에서 접속 주소 위치가 바뀌고 8에서 일부 API가 사라진 것처럼 버전 변화가 크면, 생성된 코드가 현재 버전과 맞지 않을 수 있습니다. 또 migrate처럼 데이터베이스를 바꾸는 명령은 AI가 실행하기 쉬운 만큼 위험도 커서, Prisma가 동의 절차를 따로 둔 것도 그런 위험이 실제로 있기 때문일 것입니다.

SQL 직접 작성은 AI가 비교적 익숙하게 다룰 것이라고 짐작하지만, 이 글에서 확인한 내용은 아닙니다. 대신 결과를 검증하는 일은 사람이 해야 합니다. 타입 검사가 없으면 컬럼 이름 오타나 잘못된 JOIN이 실행해 봐야 드러납니다.

정리하면 ORM은 AI가 만든 코드를 기계가 먼저 검사해 준다는 점에서, SQL 직접 작성은 쿼리를 한 줄씩 통제한다는 점에서 각각 쓸모가 있습니다. 어느 쪽이든 데이터베이스를 바꾸는 명령은 사람이 확인하고 넘어가는 것이 안전합니다.

용어 설명#

ORM#

Object-Relational Mapping(객체 관계 매핑). 코드의 객체와 관계형 데이터베이스의 테이블을 이어 주어, SQL을 직접 쓰지 않고도 데이터를 읽고 쓰게 하는 도구입니다. (Prisma 문서)

CRUD#

Create, Read, Update, Delete. 데이터를 만들고 읽고 고치고 지우는 기본 작업 네 가지입니다. (CRUD 쿼리)

JOIN#

조인. 여러 테이블의 행을 공통 키로 묶어 한 번에 조회하는 SQL 구문입니다. Prisma는 include로 관계를 가져올 때 JOIN을 직접 쓰지 않게 해 줍니다. (Is Prisma an ORM?)

MCP#

Model Context Protocol. AI 도구가 외부 서비스의 기능을 호출하도록 연결하는 규약입니다. (Prisma MCP server)

SQL#

Structured Query Language(구조화 질의 언어). 관계형 데이터베이스에 데이터를 묻고 바꾸는 표준 언어입니다. (TypedSQL)
