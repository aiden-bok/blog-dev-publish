3. GitHub 계정과 저장소 보안 설정하기

GitHub 보안은 계정부터 시작합니다. 2단계 인증을 켜서 계정을 지키고, 중요한 브랜치에는 보호 규칙을 걸고, Dependabot으로 취약한 의존성을 찾고, 비밀 정보가 담긴 푸시를 차단하는 기능을 확인하면 됩니다. 이 글은 이 네 가지가 무엇을 하고 어디서 켜는지 정리했습니다.

협업 기능은 1. GitHub 이슈, 풀 리퀘스트, 프로젝트로 협업하기, 자동화는 2. GitHub Actions, Pages, Releases, Codespaces로 자동화하기에 있습니다. 기준은 2026-11-06에 확인한 GitHub Docs입니다. 기능별 제공 범위는 요금제와 저장소 공개 여부에 따라 달라지며, 문서에서 확인되지 않은 부분은 아래에 그렇게 적었습니다. 직접 실행한 결과는 싣지 않았습니다.

2단계 인증과 passkey#

2단계 인증(2FA, Two-Factor Authentication)은 로그인에 비밀번호 외에 두 번째 확인 수단을 요구해서, 비밀번호가 새어도 계정에 들어오지 못하게 막는 기능입니다. (About two-factor authentication)

GitHub는 2023년 3월부터 GitHub.com에서 코드를 기여하는 사용자에게 2FA를 요구하기 시작했지만, 대상은 선정된 그룹입니다. 안내를 받지 않았다면 의무는 아니고, GitHub는 켜기를 강력히 권합니다. 수단은 인증 앱(TOTP), 보안 키(WebAuthn), GitHub Mobile 등이 있습니다. passkey는 비밀번호와 2FA 요구를 한 번에 만족시켜 한 단계로 로그인할 수 있게 하지만, 잠기는 사고를 줄이려면 TOTP 앱 같은 대체 수단을 함께 등록하라고 안내합니다.

브랜치 보호 규칙과 규칙 세트#

보호 규칙은 중요한 브랜치에 아무나 바로 푸시하거나 지우지 못하게 막는 설정입니다. 병합 전 풀 리퀘스트와 승인 수 요구, 상태 검사 통과, 대화 해결, 서명된 커밋, 선형 기록, 병합 대기열을 요구할 수 있고, 브랜치를 읽기 전용으로 잠그거나 푸시할 수 있는 사용자를 제한할 수 있습니다. 강제 푸시와 삭제는 기본으로 막힙니다. 관리자는 기본적으로 규칙에서 제외되며, 관리자에게도 적용하는 설정을 따로 켭니다. (About protected branches)

규칙 세트(ruleset)는 브랜치와 태그에 적용하는 이름 붙은 규칙 목록입니다. 한 브랜치에 여러 규칙 세트를 동시에 적용할 수 있고, 삭제하지 않고 활성과 비활성을 바꿀 수 있으며, 읽기 권한이 있으면 누구나 활성 규칙 세트를 볼 수 있습니다. 보호 규칙과 함께 적용되면 모두 적용되고 같은 규칙이 다르면 더 엄격한 쪽을 따릅니다. (About rulesets)

요금제별 제공 범위는 확인하지 못했습니다. 위 규칙 세트 문서는 Team과 Enterprise 요금제용이라고 적었고, 보호 규칙 문서는 푸시 제한이 Free 조직의 공개 저장소와 Team, Enterprise Cloud 조직의 모든 저장소에서 가능하다는 것만 밝힙니다. Free 개인 저장소에서 어떤 규칙을 쓸 수 있는지는 저장소의 Settings 화면에서 확인합니다.

Dependabot으로 취약한 의존성 찾기#

Dependabot은 의존성 관리 기능 세 가지를 묶은 이름입니다. 알림(alerts)은 알려진 취약점이 있는 의존성을 알려 주고, 보안 업데이트(security updates)는 그 취약점을 고치는 풀 리퀘스트를 자동으로 열고, 버전 업데이트(version updates)는 의존성을 최신으로 유지하는 풀 리퀘스트를 자동으로 엽니다. (Dependabot quickstart guide)

저장소의 Settings에서 Advanced Security를 열고 Dependabot 항목의 Enable을 누르면 켤 수 있습니다. 켜면 의존성 그래프도 함께 켜집니다. 버전 업데이트를 켜면 .github 디렉터리에 dependabot.yml이 만들어지고, 이 파일을 고쳐 설정합니다.

알림은 기본 브랜치를 검사하며, GitHub Advisory Database에 새 취약점이 추가되거나 의존성 그래프가 바뀔 때 보냅니다. 알림에는 영향받는 파일, 취약점 설명과 심각도, 고쳐진 버전이 있으면 그 버전이 나옵니다. 보관된 저장소는 검사하지 않습니다. (About Dependabot alerts)

비밀 정보 푸시를 막는 push protection#

Push protection은 하드코딩된 비밀 정보가 담긴 푸시를 저장소에 닿기 전에 차단하는 기능입니다. 알림만 보내는 것과 달리 사고를 미리 막습니다. 대상은 주요 제공자의 자격 증명, 개인 키와 데이터베이스 연결 문자열 같은 정형 비밀 정보, 직접 정의한 패턴입니다. 사용자 수준의 push protection은 기본으로 켜져 있고 GitHub.com에서 공개 저장소로 비밀 정보를 푸시하는 것을 막습니다. 저장소 수준 설정은 GitHub Secret Protection이 필요합니다. (About push protection)

차단되면 코드에서 비밀 정보를 지우고 다시 푸시합니다. 쓰기 권한이 있으면 테스트에 쓰는 값, 오탐, 나중에 고치겠음 중 사유를 골라 우회할 수 있고, 우회 기록은 감사 로그에 남으며 소유자와 관리자에게 메일이 갑니다. 이미 저장소에 올라간 비밀 정보를 처리하는 방법은 이 문서에 없습니다. 일반적으로는 노출된 자격 증명을 폐기하고 새로 발급하는 것이 먼저이지만, 이 부분은 문서로 확인한 내용이 아니라 일반적인 관행입니다.

용어 설명#

2FA#

Two-Factor Authentication(2단계 인증). 비밀번호에 더해 두 번째 확인 수단을 요구하는 로그인 방식입니다. (About two-factor authentication)

TOTP#

Time-based One-Time Password(시간 기반 일회용 비밀번호). 인증 앱이 로그인할 때 보여 주는 짧은 시간 동안만 유효한 코드입니다. (About two-factor authentication)

passkey#

비밀번호 없이 기기 인증으로 로그인하는 수단입니다. GitHub에서는 비밀번호와 2FA 요구를 한 번에 만족시킬 수 있습니다. (About two-factor authentication)
