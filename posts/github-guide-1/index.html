GitHub는 코드를 올려 두는 곳 이상입니다. 같은 저장소 안에서 할 일을 기록하는 이슈, 변경을 검토하는 풀 리퀘스트, 진행 상황을 보는 Projects를 함께 쓰면 혼자 하는 작업도 기록이 남고 협업으로 넓히기도 쉽습니다. 이 글은 GitHub에 코드만 올려 온 사용자가 가장 먼저 시도할 만한 협업 기능을 정리했습니다.

자동 검사와 배포는 2. GitHub Actions, Pages, Releases, Codespaces로 자동화하기, 계정과 저장소 보안은 3. GitHub 계정과 저장소 보안 설정하기에 있습니다. 기준은 2026-11-06에 확인한 GitHub Docs입니다. 화면과 요금제별 제공 범위는 바뀔 수 있습니다. 이 글은 문서를 근거로 정리했으며 직접 실행한 결과는 싣지 않았습니다.

Git과 GitHub는 무엇이 다른가#

Git은 파일의 변경 내용을 추적하는 버전 관리 시스템이고, GitHub는 Git 저장소를 클라우드에 두고 그 위에 계획과 협업 도구를 얹은 플랫폼입니다. (About GitHub and Git) 커밋과 브랜치는 Git의 기능이고, 이슈와 풀 리퀘스트는 GitHub가 더한 기능입니다.

GitHub 문서는 이 플랫폼의 기능을 계획, 코드 관리, 코드 리뷰, 자동 테스트, 배포, 유지보수와 보안, 협업, 호스팅과 게시, AI 도구로 나누어 소개합니다. 소스 저장소로만 쓰는 사용자는 이 가운데 코드 관리만 쓰고 있는 셈입니다.

이슈로 할 일과 버그 기록하기#

이슈는 저장소 안에서 작업을 계획하고 논의하고 추적하는 기능입니다. 버그 제보, 기능 요청, 아이디어, 피드백, 할 일에 모두 쓸 수 있고, 큰 작업은 하위 이슈로 나눌 수 있습니다. (About issues)

혼자 쓰는 저장소에서도 이슈는 유용합니다. 나중에 고칠 문제를 메모에 흩어 두는 대신 이슈로 남기면 번호가 붙고, 이후 커밋과 풀 리퀘스트에서 그 번호로 연결됩니다. 이슈에는 레이블과 마일스톤 같은 정보를 붙여 분류할 수 있고, 이슈 템플릿과 양식을 만들어 두면 제보자가 필요한 정보를 빠뜨리지 않고 적게 할 수 있습니다.

풀 리퀘스트로 변경 검토하기#

풀 리퀘스트(Pull Request, 변경 병합 요청, PR)는 코드 변경을 프로젝트에 합치자고 제안하는 기능입니다. 합치기 전에 검토자가 변경을 보고 논의할 수 있어서 문제를 일찍 찾을 수 있습니다. (About pull requests)

기본 흐름은 작업 브랜치를 만들어 커밋하고, 그 브랜치를 기본 브랜치로 합치는 PR을 열고, 검토를 거쳐 병합하는 것입니다. 아직 검토받을 준비가 안 됐다면 초안(draft) PR로 열 수 있습니다. 초안은 병합할 수 없고, 코드 소유자에게 자동으로 검토가 요청되지도 않습니다. 준비되면 ready for review로 바꾸고, 언제든 다시 초안으로 되돌릴 수 있습니다.

PR 본문에 키워드를 적으면 병합할 때 이슈가 자동으로 닫힙니다. 사용할 수 있는 키워드는 close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved입니다. (Linking a pull request to an issue)

Closes #10

이슈가 여러 개면 Resolves #10, resolves #123처럼 이슈마다 키워드를 적습니다. 다른 저장소의 이슈는 Fixes octo-org/octo-repo#100 꼴로 씁니다. 이 연결은 PR이 저장소의 기본 브랜치를 대상으로 할 때만 동작하며, 다른 브랜치가 대상이면 키워드가 무시됩니다.

Projects로 진행 상황 한눈에 보기#

GitHub Projects는 이슈와 PR을 모아 계획하고 진행 상황을 추적하는 도구입니다. 이슈, PR과 동기화되어서 어느 쪽에서 바꿔도 양쪽에 반영됩니다. (About Projects)

보는 방식은 세 가지입니다. 표(table)는 스프레드시트처럼 촘촘하게 나열하는 방식이라 백로그 정리에 맞고, 보드(board)는 칸반 방식으로 단계별 진행을 보여 주며, 로드맵(roadmap)은 일정을 타임라인으로 보여 줍니다. 날짜, 숫자, 단일 선택, 텍스트, 반복(iteration) 같은 사용자 지정 필드를 추가할 수 있습니다. 항목이 조건에 맞으면 자동으로 추가하거나 보관하는 자동화도 지원합니다.

Discussions로 질문과 의견 받기#

Discussions는 프로젝트 커뮤니티가 외부 도구 없이 열린 대화를 나누는 공간입니다. 공지, 질문과 답변, 의견 수렴, 투표에 쓸 수 있습니다. 관리자가 저장소나 조직에서 기능을 먼저 켜야 하며, 켜면 접근 권한이 있는 누구나 토론을 열 수 있습니다. (About discussions)

정해진 작업이 아니라 열린 주제라면 이슈 대신 토론이 맞습니다. 이슈로 들어온 열린 질문은 토론으로 바꿀 수 있습니다. 질문과 답변 카테고리에서는 답변을 채택 표시할 수 있습니다.

프로필 README로 나를 소개하기#

프로필 README는 GitHub 프로필 페이지 위쪽에 보이는 소개 글입니다. 사용자 이름과 똑같은 이름의 공개 저장소를 만들고, 루트에 내용이 있는 README.md를 두면 됩니다. 저장소를 만들 때 Add README를 켜면 편합니다. (Managing your profile README) 2020년 7월 이전에 만든 저장소라면 프로필에 자동으로 보이지 않을 수 있고, 이때는 저장소에서 Share to profile을 누릅니다.

용어 설명#

PR#

Pull Request(풀 리퀘스트). 작업 브랜치의 코드 변경을 다른 브랜치에 합쳐 달라고 제안하고 검토받는 GitHub 기능입니다. (About pull requests)

README#

저장소나 프로필을 소개하는 README.md 문서입니다. 프로필 README는 사용자 이름과 같은 공개 저장소의 README.md가 프로필 위쪽에 표시됩니다. (Managing your profile README)
