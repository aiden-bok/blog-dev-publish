CSP(Content Security Policy: 콘텐츠 보안 정책)는 페이지가 어떤 출처의 스크립트, 스타일, 이미지를 불러오고 실행해도 되는지를 서버가 브라우저에 알려 주는 규칙입니다. 서버가 Content-Security-Policy 응답 헤더에 규칙을 적어 보내면 브라우저가 그 밖의 코드를 막기 때문에, 공격자가 페이지에 스크립트를 끼워 넣는 XSS(Cross-Site Scripting: 교차 사이트 스크립팅) 공격의 피해를 줄일 수 있습니다.

이 글은 MDN과 web.dev 문서를 기준으로 2026-11-03에 정리했습니다. 작성 환경에서는 예시를 브라우저로 직접 실행해 보지 못해, 헤더 예시는 문서의 동작 설명을 따른 것이고 실행 결과는 싣지 않았습니다. React, Next.js, Vue에 적용하는 방법과 실무에서 많이 쓰는 정책은 2. CSP를 Next.js와 Vue에 적용하기에 나눠 두었습니다.

CSP가 필요한 이유#

CSP는 입력값 검증과 이스케이프로도 막지 못한 XSS가 실제로 실행되는 것을 한 번 더 막는 안전장치입니다. MDN은 CSP의 주된 목적이 XSS 방어이고, 입력 정제를 대신하지 않고 함께 쓰는 다층 방어(defense in depth)라고 설명합니다. (Content Security Policy, MDN)

예를 들어 댓글 입력란에서 걸러지지 않은 <script src="https://evil.example/x.js"></script>가 페이지에 들어갔다고 해 봅니다. CSP가 없으면 브라우저는 이 스크립트를 내 사이트의 코드와 똑같이 실행하고, 쿠키를 읽거나 화면을 바꿀 수 있습니다. 정책에 script-src 'self'가 있으면 브라우저는 같은 출처가 아닌 이 스크립트를 실행하지 않습니다.

XSS 말고도 클릭재킹(clickjacking)을 막는 frame-ancestors, HTTP 주소의 리소스를 HTTPS로 바꿔 요청하는 upgrade-insecure-requests 같은 지시어가 있습니다. 다만 많은 사이트가 CSP를 도입하는 가장 큰 이유는 XSS 방어입니다.

CSP의 동작 방식#

CSP는 서버가 정책을 정하고 브라우저가 지키는 구조입니다. 서버는 응답 헤더로 정책을 보내고, 브라우저는 페이지가 리소스를 불러오거나 인라인 스크립트를 실행할 때마다 정책과 비교해서 맞지 않으면 막습니다. 막힌 내용은 개발자 도구 콘솔에 오류로 나타납니다.

그림처럼 /app.js는 'self'(같은 출처)와 일치해서 실행되고, evil.example에서 온 스크립트는 정책에 없어서 차단됩니다. 정책을 보내는 서버가 스크립트를 막는 것이 아니라 비교와 차단을 브라우저가 한다는 점이 중요합니다. CSP를 이해하지 못하는 오래된 브라우저나 헤더를 제거하는 중간 장비에서는 정책이 적용되지 않습니다.

정책은 세미콜론으로 구분한 지시어(directive)의 모음이고, 지시어 하나는 이름과 허용할 값으로 이루어집니다.

Content-Security-Policy: default-src 'self'; img-src 'self' example.com

이 정책은 이미지를 제외한 모든 리소스를 같은 출처에서만, 이미지는 같은 출처와 example.com에서만 불러오게 합니다. 헤더 대신 <meta http-equiv="Content-Security-Policy"> 요소로도 정책을 둘 수 있지만, 지원하지 않는 기능이 있어 헤더가 기본입니다. (MDN)

정책을 바로 적용하지 않고 먼저 시험하는 방법#

Content-Security-Policy-Report-Only 헤더는 정책을 강제하지 않고 위반만 보고합니다. MDN은 이 헤더를 새 정책을 배포하기 전에 시험하는 용도로 안내합니다. 기존 사이트에 CSP를 처음 넣을 때는 이 헤더로 어떤 요청이 걸리는지 먼저 모으고, 정책을 다듬은 뒤에 Content-Security-Policy로 바꾸는 순서가 안전합니다. 두 헤더를 함께 보내면 강제 정책은 그대로 적용되고, 보고 전용 정책은 위반 보고만 만듭니다.

주요 CSP 지시어와 예시#

지시어는 어떤 종류의 리소스를 제어하느냐에 따라 나뉩니다. 자주 쓰는 것은 아래와 같습니다.

지시어제어하는 대상
default-src따로 지정하지 않은 리소스 종류의 기본값
script-srcJavaScript의 출처와 인라인 스크립트
style-srcCSS의 출처와 인라인 스타일
img-src이미지
connect-srcfetch, XMLHttpRequest, WebSocket 같은 연결 대상
object-src<object>, <embed> 같은 플러그인 요소
base-uri<base> 요소가 지정할 수 있는 주소
form-action폼을 전송할 수 있는 주소
frame-ancestors이 페이지를 <iframe>으로 품을 수 있는 부모 페이지
upgrade-insecure-requestsHTTP 리소스 주소를 HTTPS로 바꿔 요청

default-src는 나머지 fetch 지시어가 비어 있을 때 대신 쓰이는 기본값입니다. script-src처럼 따로 지정한 지시어가 있으면 그 종류에는 default-src가 아니라 지정한 값이 적용됩니다. frame-ancestors는 X-Frame-Options 헤더를 대신하는 지시어입니다. (MDN)

예를 들어 같은 출처의 스크립트만 허용하고 플러그인과 외부 iframe 삽입을 막는 정책은 다음과 같습니다.

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'

CSP의 핵심 키워드#

지시어 뒤에 오는 값 중 작은따옴표로 감싼 것이 키워드입니다. 따옴표를 빼면 self가 키워드가 아니라 self라는 호스트 이름으로 해석되므로 따옴표까지 써야 합니다.

키워드뜻
'self'문서와 같은 출처의 리소스만 허용
'none'그 종류의 리소스를 모두 차단 (다른 값과 함께 쓰지 못함)
'unsafe-inline'인라인 스크립트와 onclick 같은 이벤트 핸들러 허용
'unsafe-eval'eval() 같은 문자열 실행 API 허용
'nonce-값'nonce 속성값이 같은 <script>, <style>만 허용
'sha256-해시'내용의 해시가 같은 스크립트만 허용
'strict-dynamic'신뢰한 스크립트가 불러오는 스크립트도 허용

'unsafe-inline'과 'unsafe-eval'은 이름 그대로 XSS 방어를 약하게 만들기 때문에 MDN은 피하라고 권합니다. 정책에 nonce나 해시가 함께 있으면 브라우저는 같은 지시어의 'unsafe-inline'을 무시합니다. (MDN)

nonce(number used once: 한 번만 쓰는 값)는 서버가 응답마다 새로 만드는 무작위 값입니다. 헤더에 'nonce-값'을 넣고 <script nonce="값">처럼 같은 값을 태그에 붙이면 그 태그만 실행됩니다. 공격자가 주입한 스크립트에는 이 값을 붙일 수 없습니다. web.dev는 nonce 기반 CSP가 XSS를 줄이는 것은 공격자가 nonce를 추측하지 못할 때뿐이라고 설명하고, 응답마다 암호학적으로 강한 값을 새로 만들라고 권합니다. (Mitigate cross-site scripting (XSS) with a strict Content Security Policy, web.dev)

해시 방식은 서버가 매번 값을 만들 필요가 없어 정적 페이지에 맞고, nonce 방식은 서버가 HTML을 만들어 응답하는 페이지에 맞습니다. 두 방식 모두 object-src 'none'과 base-uri를 함께 두는 구성이 web.dev의 권장입니다.

Content-Security-Policy: script-src 'nonce-{RANDOM}' 'strict-dynamic'; object-src 'none'; base-uri 'none'

{RANDOM} 자리에는 응답마다 새로 만든 값이 들어갑니다. 호스트 주소를 나열하는 방식(allowlist)은 우회되기 쉬워서, web.dev는 이런 nonce나 해시 기반의 엄격한 정책(strict CSP)을 권합니다.

용어 설명#

CSP#

Content Security Policy(콘텐츠 보안 정책). 웹 페이지가 불러오고 실행할 수 있는 리소스를 제한하는 브라우저 보안 기능이며, Content-Security-Policy 응답 헤더로 설정합니다. (MDN)

XSS#

Cross-Site Scripting(교차 사이트 스크립팅). 공격자가 웹 페이지에 악성 스크립트를 끼워 넣어 다른 사용자의 브라우저에서 실행시키는 공격입니다. (MDN)

클릭재킹#

Clickjacking. 공격자가 투명한 <iframe>으로 다른 사이트를 덮어 두고, 사용자가 눈에 보이는 버튼을 누른다고 믿게 하여 숨겨진 사이트의 버튼을 누르게 하는 공격입니다. (MDN)

nonce#

number used once(한 번만 쓰는 값). CSP에서는 서버가 응답마다 새로 만드는 무작위 값으로, 헤더의 'nonce-값'과 태그의 nonce 속성이 같을 때만 스크립트와 스타일을 허용하는 데 씁니다. (MDN)
