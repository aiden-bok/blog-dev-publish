2. CSP를 React, Next.js, Vue에 적용하기와 실무 기본 정책

React, Next.js, Vue에서 CSP를 적용할 때 부딪히는 인라인 스크립트와 unsafe-eval 문제, nonce 설정 방법, 실무에서 출발점으로 삼는 기본 정책을 정리했습니다.

프레임워크 앱에 CSP(Content Security Policy: 콘텐츠 보안 정책)를 넣을 때 부딪히는 문제는 대부분 두 가지입니다. 프레임워크가 만드는 인라인 스크립트와 스타일이 정책에 막히는 문제, 그리고 개발 모드나 템플릿 컴파일이 eval 계열 API를 쓰는 문제입니다. 해결은 응답마다 nonce(number used once: 한 번만 쓰는 값)를 발급해 인라인 코드를 허용하고, 운영 빌드에서는 'unsafe-eval'을 빼는 방향으로 갑니다.

이 글은 Next.js 공식 문서(최종 수정 2026-03-20 표기), Vite 문서, Vue 소스 코드를 기준으로 2026-11-03에 정리했습니다. 작성 환경에서는 Node.js와 브라우저를 실행하지 못해, 아래 코드는 공식 문서의 설명에 맞춰 쓴 것이며 직접 실행해서 확인하지 않았습니다. CSP의 기본 개념과 지시어는 1. CSP란 무엇인가에 있습니다.

React와 Vite 앱에서 CSP가 막는 것#

Vite로 만든 React 앱은 빌드하면 index.html에 <script type="module">과 스타일 링크가 들어가고, 이 파일은 서버나 CDN이 정적으로 내려 줍니다. 그래서 같은 출처의 번들만 허용하는 script-src 'self'는 그대로 동작하는 경우가 많습니다. 걸리는 것은 두 곳입니다.

하나는 작은 에셋입니다. Vite는 빌드할 때 작은 에셋을 data: 주소로 인라인하기 때문에, 이미지와 글꼴 지시어에 data:를 허용하거나 build.assetsInlineLimit: 0으로 인라인을 끄라고 안내합니다. Vite 문서는 script-src에 data:를 허용하지는 말라고 경고합니다. (Features: Content Security Policy, Vite)

다른 하나는 nonce입니다. Vite에는 html.cspNonce 옵션이 있고, 설정하면 <script>, <style>와 모듈 preload 링크에 nonce 속성을 붙입니다. 이때 index.html에 <meta property="csp-nonce" nonce="PLACEHOLDER" />가 들어가고, 이 자리표시자를 요청마다 서버가 새 값으로 바꿔야 합니다. 정적 파일을 그대로 내려 주는 구성에서는 값이 고정되어 nonce의 의미가 없어지므로, 이 경우에는 해시 방식이나 'self' 위주 정책이 맞습니다.

React 자체는 개발 모드에서 eval을 쓰기 때문에 로컬 개발 서버에는 'unsafe-eval'이 필요할 수 있습니다. Next.js 문서는 개발 환경에서만 이 값을 넣고 운영에서는 필요하지 않다고 설명합니다.

Next.js에서 nonce를 발급하는 방법#

Next.js에서 nonce 기반 CSP를 쓰려면 요청마다 실행되는 코드에서 nonce를 만들어 헤더에 넣고, 페이지를 요청 시점에 렌더링해야 합니다. 공식 문서는 Next.js가 서버 렌더링 중에 요청의 CSP 헤더에서 'nonce-값'을 읽어 프레임워크 스크립트와 페이지 번들, <Script> 컴포넌트에 자동으로 붙인다고 설명합니다. (Content Security Policy, Next.js)

문서의 구성을 줄여 쓰면 다음과 같습니다. 문서가 요청 처리 파일로 안내하는 proxy.ts에 두는 코드입니다.

import { NextRequest, NextResponse } from 'next/server'

export function proxy(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64')
  const isDev = process.env.NODE_ENV === 'development'

  const csp = [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''}`,
    `style-src 'self' ${isDev ? "'unsafe-inline'" : `'nonce-${nonce}'`}`,
    "img-src 'self' blob: data:",
    "object-src 'none'",
    "base-uri 'self'",
    "form-action 'self'",
    "frame-ancestors 'none'",
  ].join('; ')

  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-nonce', nonce)
  requestHeaders.set('Content-Security-Policy', csp)

  const response = NextResponse.next({ request: { headers: requestHeaders } })
  response.headers.set('Content-Security-Policy', csp)
  return response
}

nonce는 응답마다 달라야 하므로 모든 페이지가 요청 시점에 렌더링되어야 합니다. 문서에 따르면 이 경우 정적 최적화와 ISR(Incremental Static Regeneration: 점진적 정적 재생성)이 꺼지고 CDN 캐시가 어려워지며, Partial Prerendering과는 함께 쓸 수 없습니다. 정적 생성을 유지하고 싶으면 문서가 실험 기능으로 소개하는 SRI(Subresource Integrity: 하위 리소스 무결성, experimental.sri) 방식이 있지만, 이 기능은 App Router에서만 되고 바뀌거나 사라질 수 있다고 적혀 있습니다. nonce를 읽어 서드파티 스크립트에 붙일 때는 서버 컴포넌트에서 (await headers()).get('x-nonce')를 쓰고, 해당 도메인은 script-src와 connect-src에 추가합니다.

Vue에서 'unsafe-eval'이 필요해지는 경우#

Vue는 브라우저에서 문자열 템플릿을 컴파일하는 빌드를 쓰면 'unsafe-eval'이 필요하고, 템플릿을 미리 컴파일하는 런타임 전용 빌드를 쓰면 필요하지 않습니다. Vue 소스의 컴파일 함수는 생성한 코드 문자열을 new Function(...)으로 함수로 바꾸고, new Function은 CSP에서 'unsafe-eval' 없이는 막히는 API입니다. (vuejs/core, packages/vue/src/index.ts, GitHub) Vue 공식 문서는 이 연결을 CSP라는 말로 설명하지는 않아서, 위 설명은 소스 코드와 MDN의 'unsafe-eval' 설명을 이어 본 것입니다.

Vue 패키지의 README는 vue.runtime.esm-bundler.js가 기본 번들러 진입점이고, 런타임 전용이라 모든 템플릿을 미리 컴파일해야 한다고 설명합니다. (vuejs/core, packages/vue/README.md, GitHub) 그래서 .vue 단일 파일 컴포넌트를 Vite로 빌드하는 일반적인 구성에서는 'unsafe-eval' 없이 동작할 가능성이 큽니다. 문제가 생기는 것은 CDN 스크립트로 Vue를 불러와 HTML 안의 템플릿을 그대로 쓰거나, createApp({ template: '...' })처럼 template 문자열을 쓰는 경우입니다. 이때는 번들러에서 컴파일러가 들어간 빌드로 바꿔 둔 것이 아닌지 먼저 확인하고, 템플릿을 .vue 파일로 옮겨 미리 컴파일하는 쪽이 정책을 지키는 길입니다.

Vue의 보안 가이드는 사용자 입력을 컴포넌트 템플릿으로 쓰지 말라는 것을 가장 기본 규칙으로 둡니다. (Security, Vue.js) CSP는 이런 실수가 있을 때 피해를 줄이는 추가 방어이지, 이 규칙을 대신하지 않습니다.

실무에서 많이 쓰는 CSP의 출발점#

실무에서는 엄격한 정책을 처음부터 강제하지 않고, 보고 전용으로 시작해서 위반을 줄인 뒤 강제로 바꿉니다. 아래는 서버가 HTML을 응답마다 만들어 nonce를 쓸 수 있는 앱을 가정한 기본 정책입니다.

Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'nonce-{RANDOM}' 'strict-dynamic'; style-src 'self' 'nonce-{RANDOM}'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests

지시어별로 정한 이유는 다음과 같습니다.

  • default-src 'self': 목록에 없는 리소스 종류는 같은 출처만 허용합니다.
  • script-src와 style-src의 nonce: 인라인 코드를 'unsafe-inline' 없이 허용합니다. 정적 페이지라면 nonce 대신 해시를 씁니다.
  • object-src 'none', base-uri 'self': 플러그인 삽입과 <base>를 이용한 주소 바꿔치기를 막습니다.
  • frame-ancestors 'none': 다른 사이트가 이 페이지를 iframe에 넣지 못하게 합니다.
  • connect-src: API 서버, 분석 도구 같은 외부 연결 주소를 사이트에 맞게 여기에 추가합니다.

운영 순서는 이렇습니다. 먼저 Content-Security-Policy-Report-Only로 배포하고 개발자 도구 콘솔이나 보고 수집 주소에 쌓이는 위반을 확인합니다. 외부 스크립트(분석, 결제, 채팅 위젯)가 막히면 필요한 주소만 추가하고, 위반이 거의 없어지면 헤더 이름을 Content-Security-Policy로 바꿉니다. 위반 보고를 받으려면 report-to 지시어와 Reporting-Endpoints 헤더를 쓰고, MDN은 report-to 지원이 넓어질 때까지 예전 방식인 report-uri도 함께 두라고 안내합니다. (MDN)

용어 설명#

CSP#

Content Security Policy(콘텐츠 보안 정책). 웹 페이지가 불러오고 실행할 수 있는 리소스를 제한하는 브라우저 보안 기능이며, Content-Security-Policy 응답 헤더로 설정합니다. (MDN)

ISR#

Incremental Static Regeneration(점진적 정적 재생성). Next.js에서 정적으로 만든 페이지를 일정 주기나 요청에 따라 다시 만드는 방식입니다. (Next.js)

SRI#

Subresource Integrity(하위 리소스 무결성). 스크립트 파일의 해시를 integrity 속성에 적어 두고, 브라우저가 내려받은 파일이 그 해시와 같을 때만 쓰게 하는 기능입니다. (MDN)

nonce#

number used once(한 번만 쓰는 값). CSP에서는 서버가 응답마다 새로 만드는 무작위 값으로, 헤더의 'nonce-값'과 태그의 nonce 속성이 같을 때만 스크립트와 스타일을 허용하는 데 씁니다. (MDN)
