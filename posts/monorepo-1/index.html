모노레포(Monorepo: 하나의 저장소)는 서로 관계가 분명한 여러 프로젝트를 하나의 Git 저장소에서 관리하는 방식입니다. 서버, 웹, 모바일 앱을 server/, web/, android/ 같은 폴더로 나눠 한 저장소에 두고, 공용 코드는 따로 패키지로 배포하지 않고 폴더째 가져다 씁니다. 저장소를 합치는 것만으로는 부족하고, 프로젝트 사이의 의존 관계를 도구가 알 수 있게 만들어야 모노레포라고 부를 수 있습니다.

이 글은 2편 중 1편으로, 모노레포의 정의와 폴더 구성, 워크스페이스 설정까지 다룹니다. AI 도구와의 관계는 2. 모노레포와 AI 코딩 도구에서 이어갑니다. 설정 예시는 각 공식 문서의 내용을 기준으로 정리했고, 이 글을 쓰는 환경에서 직접 실행해 확인한 것은 아닙니다.

모노레포는 모노리스와 무엇이 다른가#

모노레포는 저장소를 하나로 합치는 방식이고, 모노리스(Monolith: 하나로 뭉친 단일 애플리케이션)는 애플리케이션을 하나로 합치는 설계 방식입니다. 둘은 다른 이야기입니다. 모노레포 도구를 소개하는 monorepo.tools는 모노레포를 “관계가 분명한 여러 프로젝트가 들어 있는 하나의 저장소"로 설명하고, 그저 코드가 한곳에 모여 있을 뿐인 저장소와 구분합니다. (monorepo.tools)

한 저장소 안에서도 서버와 웹은 각자 빌드되고 각자 배포됩니다. 달라지는 것은 버전 관리와 변경 단위입니다. 서버의 응답 형식을 바꾸면서 웹의 호출 코드도 같은 커밋에서 고칠 수 있습니다.

반대 개념은 폴리레포(Polyrepo: 프로젝트마다 저장소를 따로 두는 방식)입니다. 서버, 웹, 안드로이드, iOS를 모두 혼자 개발하는 경우에도 저장소가 넷이면 공용 타입이나 API 규약을 바꿀 때마다 저장소 넷을 오가며 브랜치와 PR을 따로 만들어야 합니다.

모노레포의 장점과 비용#

monorepo.tools가 꼽는 장점은 패키지를 발행하거나 버전을 관리하지 않고 코드를 공유할 수 있다는 점, 여러 프로젝트에 걸친 변경을 하나의 커밋으로 묶을 수 있다는 점, 규칙을 한곳에서 통일할 수 있다는 점입니다. (monorepo.tools)

비용도 있습니다. 저장소가 커질수록 전체 빌드와 테스트 시간이 늘어나므로, 바뀐 부분만 골라 실행하는 도구가 필요해집니다. 접근 권한도 저장소 단위라서, 일부 폴더만 외부에 보여 줘야 하는 상황에는 맞지 않습니다. 혼자 또는 소수 인원이 한 제품의 여러 앱을 만드는 경우에는 장점이 크고, 서로 무관한 프로젝트를 억지로 합치면 얻는 것이 없습니다.

폴더 구성 예시#

앱은 apps/, 앱들이 함께 쓰는 코드는 packages/ 아래에 두는 구성이 흔합니다. 이름은 관례일 뿐 정해진 규칙은 아닙니다.

my-product/
├── apps/
│   ├── server/          # 백엔드 API
│   ├── web/             # 프런트엔드
│   ├── android/         # 안드로이드 앱 (Gradle 프로젝트)
│   └── ios/             # iOS 앱 (Xcode 프로젝트)
├── packages/
│   ├── shared/          # 공용 타입, 검증 규칙
│   └── api-schema/      # API 명세 (OpenAPI 등)
├── AGENTS.md
├── package.json
├── pnpm-workspace.yaml
└── turbo.json

안드로이드와 iOS 프로젝트는 각각 Gradle과 Xcode로 빌드하므로 JavaScript 패키지 관리자의 워크스페이스에는 들어가지 않습니다. 이 둘은 폴더로만 함께 두고, 서버와 공유하는 부분은 api-schema 같은 명세 파일에서 코드를 생성해 나눠 쓰는 식으로 연결하는 것이 현실적입니다.

pnpm 워크스페이스로 패키지 연결하기#

워크스페이스(Workspace: 한 저장소 안의 여러 패키지를 하나로 묶어 설치하고 서로 참조하게 하는 기능)는 npm, Yarn, pnpm이 모두 지원합니다. pnpm에서는 저장소 루트의 pnpm-workspace.yaml에 패키지가 있는 폴더를 적습니다. (pnpm Workspace)

packages:
  - apps/*
  - packages/*

패키지끼리 참조할 때는 workspace: 프로토콜을 씁니다. workspace:*로 적으면 pnpm이 레지스트리가 아니라 저장소 안의 로컬 패키지로만 해석합니다. 발행할 때는 이 값이 실제 버전 번호로 바뀝니다. (pnpm Workspace)

{
  "name": "web",
  "dependencies": {
    "shared": "workspace:*"
  }
}

특정 패키지만 실행하려면 --filter를 씁니다. pnpm --filter web test는 web만, pnpm --filter "...[origin/main]" test는 origin/main 이후 바뀐 패키지와 그것에 의존하는 패키지를 대상으로 합니다. (pnpm Filtering)

Turborepo로 빌드 순서와 캐시 관리하기#

패키지가 늘면 어느 것을 먼저 빌드해야 하는지, 바뀌지 않은 것은 건너뛸 수 있는지가 문제가 됩니다. Turborepo는 기존 package.json의 스크립트를 그대로 쓰면서, 루트의 turbo.json 하나로 작업 순서와 캐시를 정하는 빌드 도구입니다. (Turborepo)

{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    }
  }
}

dependsOn의 ^build는 어떤 패키지를 빌드하기 전에 그 패키지가 의존하는 패키지의 build를 먼저 실행하라는 뜻입니다. outputs는 캐시에 저장할 결과 파일로, 적지 않으면 파일이 캐시되지 않아 캐시가 적중해도 결과물이 복원되지 않습니다. (Configuring tasks)

turbo run build --affected는 현재 브랜치에서 바뀐 패키지와 영향을 받는 패키지만 실행합니다. 기본 비교 대상은 main과 HEAD입니다. (turbo run)

Nx도 같은 역할을 하는 도구로, 로컬 캐시와 변경 영향 범위 계산(affected)을 핵심 기능으로 둡니다. (Nx) 두 도구 중 어느 쪽이 낫다고 단정하기보다, 처음에는 pnpm 워크스페이스만으로 시작하고 빌드가 느려질 때 도입하는 순서를 권합니다.

GitHub Actions에서 바뀐 폴더만 실행하기#

CI(Continuous Integration: 지속적 통합)도 저장소 전체가 아니라 바뀐 부분 위주로 돌려야 시간이 늘어나지 않습니다. GitHub Actions에서는 워크플로 paths 필터로 특정 폴더가 바뀔 때만 실행되게 할 수 있습니다. (Workflow syntax)

on:
  pull_request:
    paths:
      - 'apps/web/**'
      - 'packages/shared/**'

주의할 점이 있습니다. 필터 때문에 워크플로가 건너뛰어지면 그 검사는 대기 상태로 남고, 브랜치 보호 규칙에서 필수 검사로 지정했다면 PR이 병합되지 않습니다. 필수 검사로 걸 워크플로는 paths 필터를 쓰지 않거나, 워크플로 안에서 변경 여부를 판단하는 방식으로 설계해야 합니다.

용어 설명#

모노레포#

Monorepo. 관계가 분명한 여러 프로젝트를 하나의 저장소에서 관리하는 방식입니다. (monorepo.tools)

모노리스#

Monolith. 여러 기능을 나누지 않고 하나의 애플리케이션으로 묶은 구조입니다. 저장소를 하나로 합치는 모노레포와는 다른 개념입니다. (monorepo.tools)

폴리레포#

Polyrepo. 프로젝트마다 Git 저장소를 따로 두는 방식입니다. 모노레포와 비교할 때 쓰는 말입니다. (monorepo.tools)

워크스페이스#

Workspace. 한 저장소 안의 여러 패키지를 함께 설치하고 서로 참조하게 하는 패키지 관리자 기능입니다. (pnpm Workspace)

CI#

Continuous Integration(지속적 통합). 코드를 합칠 때마다 빌드와 테스트를 자동으로 실행하는 과정입니다. (GitHub Actions 문서)
